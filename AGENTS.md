# AGENTS.md

This file gives coding agents the context they need to work productively in this repository.

## What this is

A small WordPress plugin (`react.php`) that lets visitors react to posts with an emoji, Facebook/GitHub-style. Reactions are stored as ordinary `wp_comments` rows with `comment_type = 'reaction'`, exposed and mutated through a custom REST route (`/wp/v2/react`), and rendered on the front end by JS built with `@wordpress/scripts`/webpack (the plugin is not related to the JavaScript library of the same name). The emoji picker itself is the third-party [`emoji-picker-element`](https://github.com/nolanlawson/emoji-picker-element) web component, not hand-rolled — see [issue #7](https://github.com/pento/react/issues/7).

## Layout

- `react.php` — plugin bootstrap. Defines `REACT_URL`/`REACT_VERSION`, loads the two classes below, and hooks `React::init()` on `init`.
- `lib/class-wp-rest-react-controller.php` — `WP_REST_React_Controller`, the REST controller for the `/wp/v2/react` route (`GET` to list/tally reactions, `POST` to add one). Validates submitted emoji against `static/emoji-data.json` (see below).
- `lib/class-react.php` — `React`, the front-end integration: enqueues assets, injects settings, filters `the_content()` to append the reaction summary + "add reaction" button.
- `src/react.js` — the JS source: imports `emoji-picker-element`, handles click interactions (opening the picker, reacting to an existing bubble), and the XHR to the REST endpoint. Bundled by webpack (`webpack.config.js`, a customized `@wordpress/scripts` config) into `static/react.js` — evergreen browsers only, no legacy-IE fallback paths.
- `static/react.css` — plain CSS (not a preprocessor). Positions/sizes the `<emoji-picker>` element and styles the reaction bubbles; the picker's own internal UI lives in its shadow DOM and isn't styled from here beyond its documented CSS custom properties.
- `static/emoji-data.json` — the emoji dataset `<emoji-picker>` renders from and the REST controller validates against, copied from the `emoji-picker-element-data` npm package by `tools/copy-emoji-data.js` (self-hosted rather than the library's CDN default, per WP.org plugin guidelines). Regenerated by `npm run build:emoji-data`, part of `npm run build`.
- `static/react.js` — the committed, built output of `src/react.js`. Regenerate with `npm run build` after changing the source; CI fails a PR that doesn't (see below).
- `tools/copy-emoji-data.js` — copies the emoji dataset into `static/` at build time (see above).
- `tools/seed-playground-data.php` — seeds demo content for the WordPress Playground blueprint; not part of the plugin runtime.
- `tests/` — PHPUnit tests using `WP_UnitTestCase`. `tests/class-wp-test-*` are copies of WP core's own REST API test helpers (excluded from WPCS as vendored code).
- `blueprint.json` — WordPress Playground blueprint; the README's "Try it now" badge points at this.

## Building / installing dependencies

```bash
composer install   # PHP dev tooling: phpcs, phpunit, wpcs
npm install         # JS dev tooling: @wordpress/scripts, emoji-picker-element(-data)
npm run build       # bundles src/react.js -> static/react.js, copies the emoji dataset -> static/emoji-data.json
```

**The build output (`static/react.js`, `static/emoji-data.json`) is committed to git**, not gitignored — this isn't optional: the WordPress Playground blueprint (`blueprint.json`) mounts the plugin directory as-is with no install/build step, and WP.org plugin distribution ships whatever's in the repo/zip directly. CI rebuilds and diffs these two files (see below) specifically to catch a PR that changed `src/react.js` without re-running `npm run build`.

## Linting and formatting

```bash
composer lint:php     # phpcs, using the WordPress-Core/Docs/Extra ruleset in phpcs.xml
composer format:php   # phpcbf, autofixes what it can

npm run lint           # wp-scripts lint-style + lint-js (static/*.css, src/*.js)
npm run lint:css       # stylelint only
npm run lint:js        # eslint only (source only -- static/react.js is bundled output, not linted directly)
npm run format          # wp-scripts format (prettier) on static/*.css, src/*.js
```

Both `composer lint:php` and `npm run lint` should pass cleanly on `master` — treat a failure as something to fix, not pre-existing noise to ignore. Known caveat: `npm run format` and `npm run lint` currently disagree about blank-line placement inside `@media` blocks in `static/react.css` (see issue #23) — don't run `format` against that file unattended.

## Running tests

Tests need a real WordPress test-suite checkout, which isn't installed by `composer install`:

```bash
bin/install-wp-tests.sh <db-name> <db-user> <db-pass> [db-host] [wp-version]
vendor/bin/phpunit
```

`tests/bootstrap.php` reads `WP_TESTS_DIR` (defaults to `/tmp/wordpress-tests-lib`) and loads the plugin via `_manually_load_react_plugin()`. If that environment isn't available, say so explicitly rather than claiming test coverage you didn't actually verify — `php -l` and `composer lint:php`/`npm run lint` are not a substitute for actually running the suite.

`src/react.js` has a small JS test suite (`src/test/react.test.js`), run via `npm run test:unit` (`@wordpress/scripts`' `test-unit-js`, i.e. Jest + jsdom). Since `src/react.js` has nothing exported, tests require it fresh with `window.wp.react.settings`/DOM fixtures already in place and drive it like a browser would (dispatched events, including a synthetic `emoji-click` on the picker), rather than importing individual functions. The real `emoji-picker-element` import is mocked away in tests (`jest.mock( 'emoji-picker-element', ... )`) rather than exercised for real -- it needs fetch/IndexedDB the jsdom environment doesn't provide, and these tests cover this plugin's glue code, not the third-party library.

All of `composer lint:php`, `vendor/bin/phpunit`, `npm run lint`, and `npm run test:unit` run in GitHub Actions (`.github/workflows/ci.yml`) on every push/PR.

## Conventions

- PHP follows WordPress-Docs/Core/Extra coding standards (tabs, Yoda conditions, full docblocks on non-test functions/methods, `esc_*()`/`wp_json_encode()` at every output boundary). Run `composer lint:php` before considering PHP work done.
- Global PHP symbols are unprefixed (`class React`, `function react_load()`) — this is a known rough edge, not a pattern to imitate in new code. See open issue on renaming `React` to something less collision-prone.
- Test methods in `tests/` don't require individual doc comments (see the `phpcs.xml` override) — their names are expected to be self-documenting.
- JS targets evergreen browsers only -- there's no legacy-IE fallback path to preserve (dropped when the plugin adopted `emoji-picker-element`, which itself doesn't support older browsers).
- Reactions are just comments under the hood; anything that changes how they're queried/counted should consider all the places WordPress surfaces comments by default (the theme's comment list, comment feeds, widgets like Recent Comments), not just the most visible one.

## Working with GitHub

- This plugin's canonical repo is `pento/react`. Real branch work happens as PRs from a fork, targeting `master`.
- The maintainer (`pento`) has been away from this project for a long time — don't `@`-mention him on issues or PRs.
- Prefer opening one focused PR per fix rather than bundling unrelated changes, and link the issue it addresses (`Fixes #N`) when it's a clean, confirmed fix. If a fix's direction is uncertain, open it as a draft rather than requesting review.
