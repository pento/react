# AGENTS.md

This file gives coding agents the context they need to work productively in this repository.

## What this is

A small WordPress plugin (`react.php`) that lets visitors react to posts with an emoji, Facebook/GitHub-style. Reactions are stored as ordinary `wp_comments` rows with `comment_type = 'reaction'`, exposed and mutated through a custom REST route (`/wp/v2/react`), and rendered on the front end by JS built with `@wordpress/scripts`/webpack (the plugin is not related to the JavaScript library of the same name). The emoji picker itself is the third-party [`emoji-picker-element`](https://github.com/nolanlawson/emoji-picker-element) web component, not hand-rolled — see [issue #7](https://github.com/pento/react/issues/7).

## Layout

- `react.php` — plugin bootstrap. Defines `REACT_URL`/`REACT_VERSION`, loads the three classes below, hooks `React::init()` on `init`, and calls `React_Settings::bootstrap()`. That bootstrap deliberately happens here rather than from `React::__construct()`: the constructor itself runs on `init`, and adding an `init` callback from inside one at the same priority is silently dropped, because `WP_Hook` iterates a copy of its callback array.
- `lib/class-wp-rest-react-controller.php` — `WP_REST_React_Controller`, the REST controller for the `/wp/v2/react` route (`GET` to list/tally reactions, `POST` to add one). Validates submitted reactions against `static/emoji-data.json` (see below) and the registered custom icons.
- `lib/class-react.php` — `React`, the front-end integration: enqueues assets, injects settings, filters `the_content()` to append the reaction summary + "add reaction" button.
- `lib/class-react-settings.php` — `React_Settings`, the **Reactions** section on Settings > Discussion: the settings and their sanitizers, the custom-icon uploader, registration of icons with WordPress 7.1's Icon Registration API, and the `is_known_reaction()` / `is_offerable_reaction()` predicates the controller and front end both use.
- `src/react.js` — the JS source: imports `emoji-picker-element`, handles click interactions (opening the picker, reacting to an existing bubble), and the XHR to the REST endpoint. Bundled by webpack (`webpack.config.js`, a customized `@wordpress/scripts` config) into `static/react.js` — evergreen browsers only, no legacy-IE fallback paths.
- `src/react-admin.js` — the JS source for the settings screen: the `<emoji-picker>` used to add default reactions, and the remove buttons. A separate webpack entry (`static/react-admin.js`) rather than a reuse of `static/react.js`, which installs a document-level click handler that posts reactions and has no business running in wp-admin. The cost is that `emoji-picker-element` is bundled twice; the two bundles never load on the same request.
- `static/react-admin.css` — hand-authored CSS for the settings section. Not build output.
- `static/react.css` — plain CSS (not a preprocessor). Positions/sizes the `<emoji-picker>` element and styles the reaction bubbles; the picker's own internal UI lives in its shadow DOM and isn't styled from here beyond its documented CSS custom properties.
- `static/emoji-data.json` — the emoji dataset `<emoji-picker>` renders from and the REST controller validates against, copied from the `emoji-picker-element-data` npm package by `tools/copy-emoji-data.js` (self-hosted rather than the library's CDN default, per WP.org plugin guidelines). Regenerated by `npm run build:emoji-data`, part of `npm run build`.
- `static/react.js`, `static/react-admin.js` — the committed, built output of `src/react.js` and `src/react-admin.js`. Regenerate with `npm run build` after changing either source; CI fails a PR that doesn't (see below).
- `tools/copy-emoji-data.js` — copies the emoji dataset into `static/` at build time (see above).
- `tools/seed-playground-data.php` — seeds demo content for the WordPress Playground blueprint; not part of the plugin runtime.
- `tests/` — PHPUnit tests using `WP_UnitTestCase`. `tests/class-wp-test-*` are copies of WP core's own REST API test helpers (excluded from WPCS as vendored code).
- `blueprint.json` — WordPress Playground blueprint; the README's "Try it now" badge points at this. Note that its `installPlugin` step pins `ref: master`, so linking to the raw file on a branch still installs master — to demo a branch, build an inline blueprint in the Playground URL fragment with `ref` set to that branch.
- `readme.txt` — the **WordPress.org** readme: user-facing description, FAQ, and the changelog, plus the `Requires at least` / `Tested up to` / `Requires PHP` headers WP.org reads. Validate changes with the `wporg-plugins` readme validator before committing.
- `README.md` — the **GitHub** readme: badges, the REST route, requirements, the hooks table, and pointers to this file. The two are deliberately separate rather than one hybrid file; the changelog lives only in `readme.txt` so they can't drift.

## Building / installing dependencies

```bash
composer install   # PHP dev tooling: phpcs, phpunit, wpcs
npm install         # JS dev tooling: @wordpress/scripts, emoji-picker-element(-data)
npm run build       # bundles src/*.js -> static/*.js, copies the emoji dataset -> static/emoji-data.json
```

**The build output (`static/react.js`, `static/react-admin.js`, `static/emoji-data.json`) is committed to git**, not gitignored — this isn't optional: the WordPress Playground blueprint (`blueprint.json`) mounts the plugin directory as-is with no install/build step, and WP.org plugin distribution ships whatever's in the repo/zip directly. CI rebuilds and diffs these three files (see below) specifically to catch a PR that changed a `src/` file without re-running `npm run build`. Adding a webpack entry means adding its output to that diff list in `.github/workflows/ci.yml` too, or the guard silently won't cover it. Note also that `output.clean` is `false` (so `react.css` and `emoji-data.json` survive a build), which means removing an entry leaves a stale committed bundle behind that nothing will flag — delete it by hand in the same commit.

## Linting and formatting

```bash
composer lint:php     # phpcs, using the WordPress-Core/Docs/Extra ruleset in phpcs.xml
composer format:php   # phpcbf, autofixes what it can

npm run lint           # wp-scripts lint-style + lint-js (static/*.css, src/*.js)
npm run lint:css       # stylelint only
npm run lint:js        # eslint only (source only -- static/*.js is bundled output, not linted directly)
npm run format          # wp-scripts format (prettier) on static/*.css, src/*.js
```

Both `composer lint:php` and `npm run lint` should pass cleanly on `master` — treat a failure as something to fix, not pre-existing noise to ignore. Known caveat: `npm run format` and `npm run lint` currently disagree about blank-line placement inside `@media` blocks in `static/react.css` (see issue #23) — don't run `format` against that file unattended.

## Running tests

Tests need a real WordPress test-suite checkout, which isn't installed by `composer install`:

```bash
bin/install-wp-tests.sh <db-name> <db-user> <db-pass> [db-host] [wp-version]
vendor/bin/phpunit
```

`tests/bootstrap.php` reads `WP_TESTS_DIR` (defaults to `/tmp/wordpress-tests-lib`) and loads the plugin via `_manually_load_react_plugin()`. If that environment isn't available, say so explicitly rather than claiming test coverage you didn't actually verify — `php -l` and `composer lint:php`/`npm run lint` are not a substitute for actually running the suite.

`src/react.js` has a small JS test suite (`src/test/react.test.js`), run via `npm run test:unit` (`@wordpress/scripts`' `test-unit-js`, i.e. Jest + jsdom). Since `src/react.js` has nothing exported, tests require it fresh with `window.wp.react.settings`/DOM fixtures already in place and drive it like a browser would (dispatched events, including a synthetic `emoji-click` on the picker), rather than importing individual functions. Settings-dependent behaviour is exercised by **mutating** the `SETTINGS` object in place between tests, never by reassigning `window.wp.react.settings` — `src/react.js` holds a reference to that exact object, so a reassignment would leave the module reading the old one. For the same reason, every new setting must be read inside a function (`settings.foo` at call time) rather than destructured at module scope, or the single `require()` in `beforeAll` would freeze it. The real `emoji-picker-element` import is mocked away in tests (`jest.mock( 'emoji-picker-element', ... )`) rather than exercised for real -- it needs fetch/IndexedDB the jsdom environment doesn't provide, and these tests cover this plugin's glue code, not the third-party library.

All of `composer lint:php`, `vendor/bin/phpunit`, `npm run lint`, and `npm run test:unit` run in GitHub Actions (`.github/workflows/ci.yml`) on every push/PR.

## Conventions

- PHP follows WordPress-Docs/Core/Extra coding standards (tabs, Yoda conditions, full docblocks on non-test functions/methods, `esc_*()`/`wp_json_encode()` at every output boundary). Run `composer lint:php` before considering PHP work done.
- Global PHP symbols are unprefixed (`class React`, `function react_load()`) — this is a known rough edge, not a pattern to imitate in new code. See open issue on renaming `React` to something less collision-prone.
- Test methods in `tests/` don't require individual doc comments (see the `phpcs.xml` override) — their names are expected to be self-documenting.
- JS targets evergreen browsers only -- there's no legacy-IE fallback path to preserve (dropped when the plugin adopted `emoji-picker-element`, which itself doesn't support older browsers).
- Reactions are just comments under the hood; anything that changes how they're queried/counted should consider all the places WordPress surfaces comments by default (the theme's comment list, comment feeds, widgets like Recent Comments), not just the most visible one.

### Version requirements

The floors are `Requires at least: 4.7` / `Requires PHP: 7.0`, declared in both `readme.txt`
and the `react.php` plugin header (the header is what WordPress itself enforces, so keep the two
in step). They come from:

- **WP 4.7** — `WP_REST_Controller`, `register_setting()`'s `$args` array form,
  `rest_authorization_required_code()`, `rest_validate_request_arg()`.
- **PHP 7.0** — a single null coalescing operator in `WP_REST_React_Controller`.

The Icon Registration API needs WP 7.1 and is `function_exists()`-gated, so it must never become
load-bearing for anything outside custom icons. Note the CI matrix only covers PHP 8.1-8.3, so
the 7.0 floor is a property of the syntax rather than something that gets exercised — if you
rely on it, extend the matrix.

### Reaction settings

Five invariants in this area are non-obvious enough that they tend to get "tidied" back into bugs:

- **`is_known_reaction()` and `is_offerable_reaction()` must stay separate.** Removing a reaction goes through the same `POST` route as adding one, so a single settings-dependent check would leave existing reactions visible but impossible to un-react after skin tones or the picker are turned off, or an icon is retired. `validate_emoji()` uses the permanent superset; the settings-dependent check happens only on the insert branch of `create_item()`.
- **Never memoize anything settings-derived in `WP_REST_React_Controller`.** The `static` cache in `get_emoji_dataset()` is safe only because the dataset is an immutable file on disk. Caching a composed allow-list would freeze at the first call in the process — wrong for the front end after a settings change, and wrong between tests.
- **Boolean settings are stored as `'1'`/`'0'`, not `true`/`false`.** `get_option()` answers `false` for an option that has never been saved and `update_option()` returns early on an unchanged value, so storing boolean `false` for a default-on setting writes nothing and unticking the box looks like it didn't save.
- **Emoji written in PHP must be the dataset's fully-qualified form.** Thumbs up is `U+1F44D U+FE0F` in `static/emoji-data.json` and a bare `U+1F44D` is not a key at all, so it gets dropped by the sanitizer. This applies to the defaults in `React_Settings::defaults()` and to `tools/seed-playground-data.php`.
- **`react_custom_icons` must not join the `discussion` option group.** `options.php` walks the group's allowed options and calls `update_option( $option, null )` for anything not submitted; icons are managed by upload rather than a matching form field, so including them would wipe every icon on each save. It's registered in its own group to keep its sanitizer and default.

## Working with GitHub

- This plugin's canonical repo is `pento/react`, and branches can now be pushed to it directly — check with `gh repo view pento/react --json viewerPermission` if unsure. PRs still target `master`. The `georgestephanis/react` remote is a fork from before that access existed; it's well behind and no longer needed.
- The maintainer (`pento`) has been away from this project for a long time — don't `@`-mention him on issues or PRs.
- Prefer opening one focused PR per fix rather than bundling unrelated changes, and link the issue it addresses (`Fixes #N`) when it's a clean, confirmed fix. If a fix's direction is uncertain, open it as a draft rather than requesting review.
